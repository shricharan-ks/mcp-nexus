# Architecture

This document describes the system architecture of MCP Gateway, its components,
data flows, and design decisions.

## Component Overview

### Operator (controller-manager)

The core component. It watches CRDs and reconciles Kubernetes resources:

| Reconciler | Watches | Creates/Manages |
|------------|---------|-----------------|
| MCPServer | `MCPServer` | Deployment, Service, health probes, Envoy route |
| MCPAgent | `MCPAgent` | Keycloak OIDC client, Envoy rate-limit config |
| MCPPolicy | `MCPPolicy` | Cerbos policy resources |
| MCPMarketplaceEntry | `MCPMarketplaceEntry` | Security scan jobs, catalog index |

Source: `cmd/operator/`, `internal/controller/`

### Envoy AI Gateway

Sits in front of all MCP servers and handles:

- **JWT validation** -- verifies tokens issued by Keycloak
- **Request routing** -- routes to the correct MCP server pod based on path
- **Rate limiting** -- enforces per-agent rate limits from MCPAgent specs
- **Protocol handling** -- supports both streamable-http and WebSocket upgrade

Configuration is generated by the operator and pushed via xDS or direct Envoy
API calls.

Source: `internal/envoy/`

### Cerbos Policy Engine

Provides attribute-based access control (ABAC):

- The operator translates MCPPolicy rules into Cerbos policy resources
- On each tool call, Envoy or the operator queries Cerbos for an allow/deny decision
- Supports role-based principals and per-tool resource scoping

Source: `internal/cerbos/`

### Keycloak (OIDC Provider)

Manages agent identities:

- Each MCPAgent gets an OIDC client in Keycloak
- Agents authenticate with client credentials and receive a JWT
- The JWT carries claims (client_id, roles) used by Envoy and Cerbos

Source: `internal/keycloak/`

### Observability Stack

OpenTelemetry instrumentation across all components:

- **Traces**: every tool call produces a span from agent to MCP server
- **Metrics**: counters, histograms, and gauges exported to Prometheus
- **Dashboards**: pre-built Grafana dashboards for operational visibility
- **Audit log**: every tool call is recorded with agent, server, tool, result, and duration

Source: `internal/observability/`, `internal/audit/`

## CRD Design

### MCPServer State Machine

```
              create
                |
                v
           +----------+
           | Pending  |
           +----+-----+
                |
                v
          +-----------+     update      +-----------+
          | Deploying +<----------------+ Updating  |
          +-----+-----+                 +-----+-----+
                |                             ^
                v                             |
          +-----------+    spec change   +----+
          |  Running  +----------------->+
          +-----+-----+
                |
         +------+------+
         |             |
    scale down    failure
         |             |
         v             v
   +-----------+  +---------+
   |  Scaling  |  | Failed  |
   +-----------+  +---------+

   delete (from any state) -> Terminating
```

Phases:

| Phase | Description |
|-------|-------------|
| `Pending` | CR accepted, waiting for reconciliation |
| `Deploying` | Deployment and Service being created |
| `Running` | All replicas ready, health checks passing |
| `Updating` | Rolling update in progress |
| `Scaling` | Replica count changing |
| `Failed` | Deployment failed or health checks failing |
| `Terminating` | Finalizer cleanup in progress |

## Data Flow: Tool Call

A complete tool call flows through the system as follows:

```
1. Agent sends HTTP POST to Envoy AI Gateway
   POST /mcp/servers/echo-server/tools/call
   Authorization: Bearer <JWT>
   Body: {"method": "tools/call", "params": {"name": "echo", "arguments": {...}}}

2. Envoy validates the JWT against Keycloak's JWKS endpoint

3. Envoy checks rate limits for the agent
   - If exceeded, return 429 Too Many Requests

4. Envoy forwards the request to the operator's auth middleware

5. The operator queries Cerbos:
   - Principal: agent identity from JWT claims
   - Action: tools/call
   - Resource: echo-server/echo
   - If denied, return 403 Forbidden

6. Request is proxied to the MCP server pod

7. MCP server processes the tool call and returns the result

8. Response flows back through Envoy to the agent

9. The entire flow is captured as an OTel trace span
   and recorded in the audit log
```

## Authentication Flow

```
Agent                  Keycloak              Envoy              Cerbos
  |                       |                    |                   |
  |-- client_credentials ->|                    |                   |
  |<---- JWT token --------|                    |                   |
  |                        |                    |                   |
  |-------- request + JWT ----------------->    |                   |
  |                        |   validate JWT --->|                   |
  |                        |<-- JWKS ---------- |                   |
  |                        |                    |                   |
  |                        |          check policy --------------->|
  |                        |                    |<-- allow/deny ----|
  |                        |                    |                   |
  |<----------- response or 403 ---------------|                   |
```

1. The agent obtains a JWT from Keycloak using the client credentials grant.
   The client ID and secret come from the MCPAgent's OIDC registration.

2. Envoy validates the JWT signature against Keycloak's JWKS endpoint and
   extracts the claims (client_id, roles, scope).

3. Envoy (or the operator middleware) sends a check request to Cerbos with the
   principal, action, and resource extracted from the JWT and the request path.

4. If Cerbos returns ALLOW, the request proceeds to the MCP server.
   If DENY, a 403 is returned to the agent.
